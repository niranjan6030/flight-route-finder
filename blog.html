No direct flight? How I built a flight route finder with Dijkstra and A*

BCA, CHRIST (Deemed to be University), Bengaluru  |  October 2026

Big cities have direct flights to each other. Small airports do not. In the data I used, Mysuru has flights only to Bengaluru, and Shillong only to Kolkata. So somebody who wants to go from Mysuru to Shillong has to change planes, and first has to work out where to change.

For my routing assignment I built a web page that works this out for any two airports in the world. This post explains the problem, the algorithm, how I tested it and how fast it is. The working prototype is here: open the flight route finder.

1. The problem

Given a starting airport and a destination, find the chain of flights that is best for the passenger. "Best" can mean three different things:

  • reaching the quickest,
  • taking the fewest flights,
  • flying the shortest distance.

There is one more thing I wanted. Sometimes an airport cannot be used: it is shut because of fog or a cyclone, or the passenger cannot pass through that country without a transit visa. Then the route has to go round that airport.

As a graph problem: every airport is a node, every flight is a directed edge with a cost, and I need the cheapest path from one node to another. This is called the single-pair shortest path problem.

Inputs and outputs

Input
  • From and To airport. The user types a city, an airport name or the 3-letter code, or clicks a dot on the map.
  • What matters most: quickest, fewest flights or shortest distance.
  • Hours wanted between two flights (1 to 4), and any airports to avoid.
  • The network: 3,257 airports with latitude and longitude, and 37,042 routes.
Output
  • The flights to take in order, with the km and time of each one, and the total.
  • Where to change planes, and up to 3 other routes to choose from.
  • The route on a world map, and a link to check each flight on Google Flights.
  • How many airports the search had to look at.

The data

The airports and routes are from the OpenFlights open database. It needed cleaning, so I wrote a Python script (tools/build_data.py):

  • airports without a 3-letter code are dropped;
  • the same route is listed once for every airline, so I keep each (from, to) pair once. 67,663 rows became 37,042;
  • 20 Indian city names in the file are old or misspelt (Madras, Bangalore, Patina). I changed them to the names used now.

What is left is 3,257 airports in 225 countries. 820 routes have no flight back in the data, which is why the graph has to be directed.

2. The algorithm

The cost of one flight

Every flight has a cost a × km + b, where km is the great circle distance between the two airports (haversine formula). Only a and b change, so one search function does all three kinds of "best".

Best meansabThe total is in
Shortest distance10km
Quickest1/8000.5 + waithours (800 km/h, plus half an hour per flight)
Fewest flights0.0000011flights (the tiny km part only breaks ties)

The important thing is that no cost is ever negative. That is what Dijkstra's algorithm needs.

Dijkstra's algorithm

  1. The start gets cost 0, every other airport gets infinity. Put the start in a min-heap.
  2. Take the airport with the smallest cost out of the heap. Its cost is now final, I call it "finished".
  3. For every flight out of it: if going this way is cheaper than what the next airport has now, write down the new cost, note where it came from, and put it in the heap.
  4. Repeat 2 and 3 until the destination is finished. Then walk back through the notes to get the route.

A*: the same thing with a guess

Dijkstra spreads out from the start in every direction, like a circle growing. Going from Kochi to Toronto it also looks at flights to Australia, which is a waste.

A* fixes that with one change. The heap is ordered by cost so far + a guess of the cost still to go. My guess is the cost of one direct flight from that airport to the destination. No real route can be cheaper than a direct flight, so the guess is never too high, and that is the condition for A* to still give the best answer. Airports in the wrong direction get a big guess and sink in the heap.

function guess(net, u, dst, cost) {
  if (u === dst) return 0;
  return cost.a * greatCircleKm(net.lat[u], net.lon[u], net.lat[dst], net.lon[dst]) + cost.b;
}

// inside aStar(), for the airport u that just came out of the heap:
for (var k = 0; k < to.length; k++) {
  var v = to[k];
  if (done[v] || closed[v]) continue;          // closed = airports the user wants to avoid
  var c = best[u] + cost.a * km[k] + cost.b;
  if (c < best[v]) {
    best[v] = c;
    prev[v] = u;
    heap.push(v, c + guess(net, v, dst, cost));
  }
}

If the guess is always 0, this is exactly Dijkstra. All of it is in js/routing.js, about 400 lines of plain JavaScript.

3. The prototype

The prototype is a web page made with HTML, plain JavaScript, Bootstrap and the Leaflet map library. There is nothing to install and it works on a phone. It draws the world map itself from a land outline file, so it even works without internet. Open it here and click one of the examples under the button.

  • Next to every change of planes there is "avoid this airport". One click and it finds a way round.
  • You can pick another route from the list and it is drawn on the map.
  • A "How was this found?" box draws the airports that Dijkstra and A* looked at, so you can see the difference.

This is Kochi to Toronto. Both give the same answer (change at Dubai). Dijkstra spreads in every direction, A* goes towards the destination. This trip is a very good case for A*, the average is in the experiments below.

5. Why this algorithm?

I did not want to just say "Dijkstra is the standard one". So I wrote five methods and timed them on the same 100 random trips, with the "quickest" cost on the full network. The time is for one search.

MethodBest route?TimemsWhat I found
Breadth first searchFewest flights onlyO(V + E)0.14Does not look at km or hours. It was not the quickest route in 72 of 100 trips.
Dijkstra without a heapYesO(V²)13.15Looks through all the airports every time to find the next one.
Bellman-FordYesO(V · E)1.09Made for negative costs, which I do not have. It cannot stop early.
Floyd-WarshallYes, all pairsO(V³)not triedAbout 3.5 × 1010 steps and a table of 10.6 million numbers, to answer one question.
Dijkstra with a min-heapYesO((V + E) log V)0.6321 times faster than without the heap.
A* (what the page uses)Yessame in the worst case0.28Same answers. Finishes about 1 airport in 6.

Why Dijkstra and A* fit this problem:

  • The costs are never negative, so Dijkstra is correct and Bellman-Ford's extra work is not needed.
  • I need one start and one destination, not all pairs, so Floyd-Warshall is far too much.
  • The network is sparse: 11 routes per airport on average, only 0.35% of all possible pairs. A heap with adjacency lists pays off on a graph like that.
  • Every airport has a position, so the straight line guess for A* costs nothing extra to get.
  • The answer has to come while the user is waiting.

V = 3,257 airports and E = 37,042 routes. If I had stored the network as a V × V table it would need 10.6 million cells. The adjacency lists need 37,042 entries.

One honest detail about the heap: when I find a cheaper cost for an airport I push a new copy instead of changing the old one, and skip the old copy when it comes out. That keeps the code simple, but the heap can grow up to E in the worst case. I measured it: the biggest heap was 1,028 items on average for Dijkstra and 862 for A*, so in practice it stays small.

7. Experiments

Everything was measured on the experiments page, which anyone can run again. I used random pairs of airports that have a route between them, and the same pairs for every method. The numbers are from Chrome 154 on my MacBook Air (M4).

Time for one search when the network grows

For this I kept only the busiest 200, 400, 800 and 1,600 airports and then all 3,257. The vertical axis is a log scale. The heap matters the most: at 3,257 airports Dijkstra takes 11.8 ms without it and 0.65 ms with it. Going from 200 to 3,257 airports, the version without a heap got 98 times slower and the version with a heap only 8 times.

What I take from these numbers:

  • A* finishes only 12 to 27% of the airports that Dijkstra does. It helps least for "fewest flights", because there the guess is almost the same (1 flight) for every airport.
  • But A* is only about 2 times faster, not 6. Every guess needs the distance formula with sin and cos, and that costs time. Fewer airports does not mean the same amount less time.
  • Bellman-Ford needed only about 6 passes and not 3,256, but it still looked at 213,010 flights for one trip. Dijkstra looked at 12,971.

8. Who can use it, and what it cannot do

  • People in small towns who need to know where to change (Hubballi to Leh, for example).
  • When a hub is shut by fog or a cyclone: click "avoid" and see the next best way.
  • People who cannot pass through a country without a transit visa.

It is different from a booking site because it is not tied to one airline, it lets you rule out airports, and it shows how the answer was found.

The limits are real though:

  • The routes in the data are from 2014. Some of those flights do not run now and new ones are missing. Always check with the airline.
  • There is no timetable. The wait between two flights is the same number at every airport.
  • There are no ticket prices.
  • It does not know that two airports can be in the same city.

Next I would like to use real schedules, so that the cost becomes the real arrival time, and add price as a fourth kind of cost.

What I learned

The part that surprised me was the A* result. It looked at about one sixth of the airports, and I expected it to be six times faster, but it was only twice as fast. Counting steps and measuring time are not the same thing, and I would not have known that without running the experiment.
